# 20.01 Runtime and Connectors

The runtime and connector crates turn source-specific knowledge access into
recoverable, deduplicated, provenance-aware sync operations.

## Connector Contract

Connectors implement the shared source contract:

- `source_id` identifies the source instance;
- `source_kind` declares source class such as Wikipedia, PubMed, or customer
  private corpus;
- `capabilities` describes currently implemented discover, fetch, delta,
  live-query, and license behavior;
- `discover`, `fetch`, and `delta` provide source-specific access paths.

The connector boundary is deliberately source-aware. A PubMed connector should
surface PMID, DOI, MeSH, and publication metadata. A customer corpus connector
should preserve tenant and ACL-relevant metadata. A Wikipedia connector should
preserve page and revision identity when available.

External database and API-feed connectors should declare source identity,
endpoint URI, auth mode, access pattern, delta/revision support, structured
metadata support, license metadata support, and access-control behavior. They
should not embed database drivers, indexing engines, or secret material in this
library. The embedding Wendao-side server owns secret injection, source-specific
execution, scheduling, and downstream indexing.

Capabilities are not aspirational. Until a connector has tested runtime
execution, it must not advertise discover, fetch, delta, local-mirror, or
live-query support. PubMed, Wikipedia, legal, paid database, and news live
sources remain out of scope for this phase, and the current crates intentionally
carry no HTTP client dependency. The repository enforces this with a phase
guard that rejects direct live-client or scheduler dependencies and live-client
imports inside connector sources.

## Runtime Contract

`wendao-nexus-runtime` owns the orchestration layer:

- job registry facade;
- source registry facade;
- checkpoint registry facade;
- content hash registry for dedup;
- artifact store facade and local filesystem backend for raw source payloads
  and normalized document sidecars;
- raw-to-normalized document normalization boundary;
- sync runtime that records pending, running, succeeded, failed, skipped,
  cached, and deduped states;
- deterministic in-memory registry for tests and early embedding.

Wendao-side persistent databases, indexing, vector search, lexical search, graph
expansion, hot cache, and rerank engines are outside this library. Nexus runtime
state is limited to trait surfaces, deterministic fixture validation, replay
artifacts, and normalized evidence handoff.

## Normalization Contract

`KnowledgeDocumentNormalizer` turns a fetched `RawSourceDocument` into an
`ExternalKnowledgeDocument`. The runtime ships a deterministic
`PlainTextNormalizer` for early mirror tests and fixture corpora. It is a
contract shim for already-text payloads, not a production parser and not a
Docling replacement.

Attachment and binary document parsing stays on the Rust Wendao side. Wendao
connects Nexus, schedules document extraction, calls its Docling-backed
attachment pipeline, and then routes parsed evidence into agent/index flows.
Nexus only keeps extraction resource shapes as protocol-level handoff contracts
when a consumer needs to describe Wendao extraction output without importing
`xiuxian-*` crates.

Source-specific parsing for PubMed XML, Wikipedia HTML, PDFs, Markdown, Docling
artifacts, or customer database rows belongs to Wendao-side parser/backends.
Those systems should emit Nexus-owned `RawSourceDocument` or
`ExternalKnowledgeDocument` records when they want provenance, trust metadata,
and Arrow/Flight handoff.

The standard metadata key contract is intentionally broader than the current
fixture parser shim. It names common bibliographic fields such as authors, DOI,
PMID, license, publication/update timestamps, version, and revision id, plus the
first vertical pack fields for customer SOPs, legal clauses, and agriculture
market signals. Wendao-side parsers and source backends populate those keys;
Nexus preserves and exposes them.

`NexusSyncRuntime::ingest_once` composes:

- connector fetch;
- content hash dedup;
- normalization;
- checkpoint update with last content hash and revision metadata.

`NexusSyncRuntime::ingest_once_with_artifact_store` adds an explicit artifact
mirror to the same flow. It writes the raw source payload before normalization
and writes the normalized `ExternalKnowledgeDocument` JSON sidecar for replay
and audit. It does not write a knowledge store.

`NexusSyncRuntime::accept_normalized_document` is the Wendao-side handoff path
for already parsed evidence. Rust Wendao can run attachment/Docling extraction,
build an `ExternalKnowledgeDocument`, and ask Nexus to record the content-hash
dedup signal and checkpoint without giving Nexus ownership of the
parser or agent scheduler. Nexus validates that document identity, canonical URI,
provenance, and content hash agree before accepting the handoff.

The `wendao-nexus-flight` provider remains the integration point. Wendao-side
code implements `NexusFlightCommandHandler` over its own storage, memory, search,
open, compare, and sync runtime.

The facade crate exports `NexusFixtureHarness` as a serverless fixture Flight
harness. It loads a deterministic `SourcePack`, ingests enabled local corpus
connectors through `NexusSyncRuntime`, mirrors raw and normalized artifacts, and
then dispatches typed command envelopes through `NexusFlightBatchProvider`.
This is the current no-server and no-backend-database proof that Wendao can
mount Nexus as an internal provider and receive Arrow search/open/status/compare
batches with provenance. The harness owns only fixture behavior; its internal
evidence view is not a public local mirror, knowledge store, or search engine
API.

## Wendao Query Ownership

Nexus does not define `LocalKnowledgeStore`, an in-memory knowledge store, or a
memory engine. Search, open, compare, persistent database storage, production
indexing, and memory integration belong to the Wendao backend after it consumes
Nexus evidence through Arrow/Flight contracts.

## Current Connector Slice

The skeleton includes:

- `StaticKnowledgeConnector` for deterministic tests and early protocol proof;
- `LocalCorpusConnector` for deterministic JSONL and Markdown fixture corpora;
- `SourcePack` for TOML/JSON manifests that group multiple deterministic local
  corpus sources;
- `ExternalDatabaseConnector` as a generic external database/API-feed boundary
  for endpoint, auth-mode, access-mode, and source identity contracts;
- `WikipediaConnector` as a typed unsupported-live stub;
- `PubMedConnector` as a typed unsupported-live stub;
- `CustomerCorpusConnector` as the private corpus boundary stub.

Live API behavior should be added only with source-specific rate limit, retry,
auth, fixture, provenance tests, and an explicit dependency review.

## Deterministic Validation First

The current runtime milestone is not live source coverage. It is a repeatable
local proof that a source can move through:

```text
static connector
  -> discover
  -> fetch
  -> normalize
  -> content hash dedup
  -> registry job/checkpoint state
  -> normalized evidence handoff
  -> test-only fixture handler
  -> Arrow RecordBatch output
  -> Flight command encode/decode
```

`StaticKnowledgeConnector`, `InMemoryNexusRegistry`, `NexusSyncRuntime`, the
fixture harness evidence view/handler, and `NexusFlightBatchProvider` are the
first closed loop for this.
`LocalCorpusConnector` extends that loop from in-code fixtures to file-backed
JSONL/Markdown source-pack fixtures. Its small frontmatter reader is only a
fixture convenience, not a Markdown parser contract. `SourcePack` adds a
deterministic manifest layer with pack id, version, default authority, source
kind, source authority, license, fixture paths, and `NexusSourceRecord` emission
while leaving ingest and scheduling to `NexusSyncRuntime`. The serverless
`NexusFixtureHarness` extends this into a no-server/no-backend-database path by
combining source pack registry loading, ingest, artifact mirror writes, command
decode, fixture-only trust-aware ranking/compare checks, and Arrow batch
inspection.
Real connectors should be added only after this deterministic path stays stable
under schema and batch snapshot tests.

## Business Scenario Fixtures

The business scenarios are deterministic vertical source packs:

```text
medical baseline corpus
  -> PubMed-style article metadata
  -> clinical guideline evidence
  -> trial_result/guideline evidence kinds
  -> PeerReviewed/Curated provenance

customer private SOP corpus
  -> source pack registry records
  -> ACL/tenant/department metadata
  -> local corpus connector
  -> runtime ingest
  -> CustomerInternal provenance

legal compliance corpus
  -> jurisdiction/statute/article metadata
  -> law_clause evidence kind
  -> Official provenance

agriculture market corpus
  -> region/crop/price-date metadata
  -> market_signal evidence kind
  -> Official provenance
```

The customer private fixture pack models tenant-owned SOPs with `tenant_id`,
department, document kind, owner team, ACL tags, version, effective date, and
customer-confidential license policy. It also includes a disabled API-feed
source record to prove that future customer database sources can appear in the
registry without creating connectors or scheduled work in this repo.

The legal and agriculture packs model vertical source fields without introducing
a full `DomainSchema` type system yet. They keep legal clauses and market
signals visible through the existing Arrow `evidence_kind` column so agents can
distinguish law clauses and market signals from generic documents.

This keeps the commercial path concrete without introducing live CRM, document
system, customer database, external market API, search, memory, CocoIndex, or
Wendao adapter ownership.

Positive business packs are directory-first fixtures:

```text
tests/fixtures/source_packs/<pack>/
  source_pack.toml
  documents.jsonl
  expected_search.snap
  expected_open.snap
  expected_status.snap
```

The `.snap` files are ordinary UTF-8 golden text consumed by unit tests; no
snapshot-test dependency is introduced. Flat source-pack manifests remain for
negative validation cases such as duplicate source ids or unsupported manifest
schema versions.

## Source Pack Manifest

The current manifest format is intentionally local and deterministic:

```toml
[source_pack]
id = "medical-baseline-pack"
version = "2026.04-fixture"
schema_version = 1
domain = "medical"
display_name = "Medical Baseline Pack"
producer = "wendao-nexus-fixtures"
authority_level = "Curated"
license = "Fixture License"

[[sources]]
source_id = "demo-pubmed"
kind = "PubMed"
fixture_path = "documents.jsonl"
display_name = "Demo PubMed Fixture"
license = "PubMed Fixture License"
authority_level = "PeerReviewed"

[[sources]]
source_id = "demo-guideline"
kind = "MedicalJournal"
fixture_path = "guideline.jsonl"
authority_level = "Curated"
```

The same shape is accepted as JSON. TOML and JSON manifests are both covered by
unit tests so source-pack authors can choose the format that best fits their
pack generation tooling.

`SourcePack` resolves `fixture_path` relative to the manifest file, returns
local corpus connectors, and emits `NexusSourceRecord` rows for source registry
implementations. It does not start jobs, write stores, or decide live source
policy. Pack ids, versions, domains, and source ids are registry identities.
`schema_version` defaults to `1`, is emitted as `source_pack_schema_version`,
and must match the current manifest contract. `producer` is optional descriptive
metadata for fixture builders or future SourcePack exporters and is emitted as
`source_pack_producer`; it does not imply execution ownership. `domain` defaults
to `generic` and is emitted as `source_pack_domain` in source registry metadata.
Per-source `display_name` and `license` override the source catalog row display
name and license policy without changing connector execution.
A manifest is invalid when pack ids, versions, producers, display names,
licenses, canonical URI prefixes, or source ids are empty or whitespace-padded.
Source ids must also be unique across the pack. Fixture paths are kept
trim-exact so deterministic packs cannot accidentally point at different files
in different shells.

Disabled source entries remain in `source_records()` with `enabled = false` so a
Wendao-side source registry can display or audit them, but `SourcePack::from_path`
does not create connectors for those entries. A pack with no enabled sources is
rejected when loading connectors because it cannot drive a deterministic ingest
loop. Source-pack registry records use the same deterministic local-corpus
capability shape as `LocalCorpusConnector`, including discover, fetch, delta,
local mirror, revision metadata, license metadata, and access-control metadata.

## CocoIndex Boundary

CocoIndex can be studied as a general incremental dataflow system and may later
feed Nexus through an optional SourcePack exporter. It should not become a core
dependency of this repository. Nexus-owned contracts remain the normalized
document, evidence kind, provenance, authority, source-pack manifest, artifact,
and Arrow Flight evidence boundary.

## Registry Traits

- `SourceRegistry`;
- `JobRegistry`;
- `CheckpointRegistry`;
- `ContentHashRegistry`.

`InMemoryNexusRegistry` implements these traits for deterministic tests and
embedded provider validation. Persistent implementations belong to the Wendao
backend or Wendao-side adapter because that side owns database selection,
deployment, migrations, and operational recovery. Wendao-side handlers should
expose registered source state through `/knowledge/external/status`.

## Artifact Store

`ArtifactStore` is the byte-level persistence boundary. It is deliberately not
part of a knowledge store: artifacts answer replay and audit questions, while
Wendao-side backends answer search/open/list questions.

The first backend is `LocalFileArtifactStore`. It writes:

```text
<root>/<source_id>/<external_id>/<artifact_kind>/<content_hash>.payload
<root>/<source_id>/<external_id>/<artifact_kind>/<content_hash>.artifact.json
```

The descriptor records source identity, external id, artifact kind, media type,
byte length, content hash, relative payload path, creation time, and metadata.
Local artifact writes are content-addressed and idempotent: if the descriptor
and payload already exist for the same source id, external id, artifact kind,
and content hash, the backend returns the existing descriptor rather than
rewriting unchanged sidecars.
The current runtime writes two artifact kinds:

- `RawSourcePayload`;
- `NormalizedDocument`.

Future object-store, Parquet, or content-addressed artifact backends should
implement the same trait without changing connector, normalizer, or Flight
contracts.

## Wendao Access Modes

Wendao should support both local mirror and federated live query modes. Nexus
only provides connector contracts, source identity, normalization, provenance,
content hash, and Arrow/Flight handoff types for those modes. The default query
path, cache policy, and live-source fallback belong to the Wendao backend.
